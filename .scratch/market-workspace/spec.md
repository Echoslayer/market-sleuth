# 台股市場工作台

## Problem Statement

目前 market-sleuth 的前端只有單一歷史回放遊戲。使用者除了未來想加入多種市場遊戲，也需要一個供自己日常理解市場的總體資訊入口。不同遊戲會使用行情、價格走勢、新聞，未來也可能使用 EPS 與財報等相同資訊，但目前沒有一份獨立於遊戲 `Scenario` 的市場資料合約，也沒有能瀏覽這些資訊的工作台。

若直接把總體市場資訊塞進既有 `Scenario`，遊戲的歷史回放合約會逐漸變成萬用 schema；若讓遊戲依賴某個頁面，又會把資料能力錯誤綁在 UI 上。需要建立獨立的 market snapshot，讓市場工作台與各遊戲都能成為同一組底層市場資訊的消費者，同時保留遊戲自己的互動合約。

## Solution

建立一個以台股為第一個範圍、桌面優先的市場工作台，並將它設為前端預設首頁。工作台讀取 pipeline 產生的每日 JSON market snapshot，顯示主要指數、自選股、日 K 線、成交量、全市場新聞與標的相關新聞。使用者可在同一頁選取標的，並依標的、日期區間與新聞類別篩選資訊。

market snapshot 使用獨立且明確的資料集合，不修改既有遊戲 `Scenario`。第一版包含 `instruments`、`priceSeries` 與 `newsItems`；未來 EPS 或財報資料真正接通後，再增加 `earnings` 等明確集合。工作台與遊戲可以共用適合共用的市場型別、查詢邏輯與展示元件，但不讓遊戲從工作台頁面取得資料。

真實 market snapshot 只供本機使用，不提交或公開部署；公開 GitHub Pages 僅使用可再散布的 toy snapshot。前端不直接呼叫第三方市場 API，不持有 API 金鑰，也不承擔 CORS、限流或資料授權責任。

## User Stories

1. 身為市場研究者，我想要打開專案就看到市場工作台，這樣我就能先理解整體市場，而不是被直接帶進單一遊戲。
2. 身為市場研究者，我想要看到主要台股指數的最新每日快照，這樣我就能快速掌握大盤方向。
3. 身為市場研究者，我想要看到一份由資料產生端管理的自選股清單，這樣我就能專注在目前追蹤的標的。
4. 身為市場研究者，我想要在總覽中比較各標的的最新價格與漲跌，這樣我就能決定下一步要深入查看哪一檔。
5. 身為市場研究者，我想要在同一頁選取標的，這樣我就能更新詳細資訊而不必離開工作台。
6. 身為市場研究者，我想要查看所選標的的日 K 線，這樣我就能理解一段時間內的價格走勢。
7. 身為市場研究者，我想要搭配 K 線查看成交量，這樣我就能把價格變化放回市場參與程度的脈絡。
8. 身為市場研究者，我想要切換圖表期間，這樣我就能用不同時間尺度觀察同一標的。
9. 身為市場研究者，我想要看到全市場重要新聞，這樣我就能理解可能同時影響多個標的的背景事件。
10. 身為市場研究者，我想要看到與所選標的相關的新聞，這樣我就能聚焦在該公司的資訊脈絡。
11. 身為市場研究者，我想要在全市場新聞與標的新聞之間切換，這樣我就能控制目前觀察的資訊範圍。
12. 身為市場研究者，我想要依標的篩選新聞，這樣我就能比較特定公司受到哪些事件影響。
13. 身為市場研究者，我想要依日期區間篩選新聞，這樣我就能把事件與價格區間對齊。
14. 身為市場研究者，我想要依新聞類別篩選，這樣我就能聚焦在總經、產業、公司、財報或政策法規等不同訊號。
15. 身為市場研究者，我想要一則新聞可同時屬於多個類別，這樣跨公司與產業的事件不會被迫放進單一分類。
16. 身為市場研究者，我想要新聞預設按最新時間排序，這樣我就能先看到目前最需要處理的資訊。
17. 身為市場研究者，我想要閱讀新聞原文，這樣我就能自行檢查摘要與脈絡。
18. 身為繁體中文使用者，我想要在有資料時看到繁中摘要，這樣我就能更快理解外語新聞。
19. 身為市場研究者，我想要看到資料最後更新時間，這樣我就能自行判斷每日快照是否足夠新。
20. 身為市場研究者，我想要在手機上仍能基本瀏覽工作台，這樣臨時查看時不會因桌面多欄版面而無法操作。
21. 身為遊戲玩家，我想要從工作台進入目前的歷史回放遊戲，這樣市場研究與遊戲仍是同一個產品內的不同入口。
22. 身為遊戲玩家，我想要現有遊戲維持原本的回合、評分與揭露行為，這樣新增工作台不會改變已經可玩的內容。
23. 身為開發者，我想要 market snapshot 與遊戲 `Scenario` 使用獨立合約，這樣市場資料增加時不會污染遊戲互動模型。
24. 身為開發者，我想要工作台與遊戲只共用真正相同的型別、查詢邏輯與展示元件，這樣未來加入第二種遊戲時能重用能力而不依賴頁面。
25. 身為資料維護者，我想要由 pipeline 管理第一版的固定自選清單，這樣前端不會允許加入一個快照中根本沒有資料的標的。
26. 身為資料維護者，我想要 pipeline 產生可驗證的 market snapshot，這樣前端能穩定消費每日行情與新聞。
27. 身為資料維護者，我想要新聞帶有零個或多個相關 symbols，這樣沒有 symbol 的新聞可視為市場層級，有 symbols 的新聞可供標的篩選。
28. 身為資料維護者，我想要新聞類別使用固定的多選分類，這樣篩選 facets 不會因自由文字而失控。
29. 身為資料維護者，我想要真實 market snapshot 保持本機私有，這樣不會違反真實新聞與市場資料的再散布限制。
30. 身為公開網站訪客，我想要看到一份可再散布的 toy snapshot，這樣公開部署仍能展示工作台而不洩漏真實資料。
31. 身為未來遊戲開發者，我想要從市場資料中挑選遊戲所需的子集合，再轉成該遊戲自己的合約，這樣不同遊戲可以加入各自的互動邏輯。
32. 身為未來功能開發者，我想要在資料真正存在時加入明確的 `earnings` 等集合，這樣 EPS 與財報能擴充進工作台而不需要預先維護通用 widget schema。

## Implementation Decisions

- 市場工作台是前端預設首頁；現有歷史回放遊戲保留為獨立入口。
- 第一版不新增路由套件。使用前端原生可處理的簡單頁面狀態或 URL 導覽，直到實際出現需要完整路由的多遊戲結構。
- 工作台採 master-detail 結構：總覽呈現主要指數與自選股；選取標的後，同頁更新走勢與標的新聞。
- 介面以桌面多欄工作台為主要情境，手機使用分頁或垂直排列維持基本可用性。
- 第一版垂直切片使用一個主要台股指數、三個自選股與一小批分類新聞。
- 自選清單由 pipeline 輸入管理。前端不提供新增或移除標的功能。
- 第一版只處理日線與每日收盤後快照，不支援分鐘線或盤中即時更新。
- 圖表顯示日 K 線與成交量，提供少量期間切換；不加入技術指標或畫線工具。
- market snapshot 是獨立於 `Scenario` 的合約。兩者可共用價格點等真正相同的基礎型別，但互不繼承，也不把 market snapshot 直接當成遊戲回合資料。
- market snapshot 至少包含 snapshot 識別資訊、`generatedAt`、`instruments`、各標的 `priceSeries` 與 `newsItems`。
- instrument 從第一版就明確帶有 symbol、名稱、種類、exchange、currency 與 timezone，以正確表達台股與主要指數；第一版顯示規則只需支援台股。
- news item 包含日期時間、標題、原文內容或可顯示的內容、可選原文 URL、可選繁中摘要、零個或多個相關 symbols，以及一個或多個 categories。
- 新聞固定分類為：總經、產業、公司、財報、政策法規、其他。一則新聞可有多個分類。
- 沒有相關 symbols 的新聞視為市場層級；帶有 symbols 的新聞可出現在相關標的資訊中。工作台提供市場／標的新聞範圍切換。
- 新聞預設最新優先。若未來資料提供 importance，可另加排序方式，但第一版不依賴它。
- market snapshot 不包含遊戲事後答案 `isKeyEvent`；市場工作台不得用這個欄位排序或篩選新聞。
- 前端支援標的、日期區間與新聞類別篩選。篩選 facets 從結構化資料產生，不建立通用篩選引擎。
- 前端固定顯示 `generatedAt`。第一版不實作交易日曆或自動過期判定。
- UI 使用繁體中文。新聞保留原文，資料有繁中摘要時才顯示；前端不執行翻譯。
- Pipeline 產生 JSON 檔，前端以既有 runtime fetch 模式讀取。前端不直接串接 yfinance、新聞來源或任何需要金鑰的 API。
- 真實 market snapshot 與真實新聞維持 gitignored，只供本機使用。公開部署只包含 allowlisted toy snapshot。
- 第一版不改既有 `Scenario`、round state、評分、揭露邏輯或遊戲資料產生流程。
- 共用既有圖表能力時，調整介面只限於工作台真正需要的 K 線、成交量與期間顯示；不為未來遊戲預建抽象。
- 未來 EPS 與財報資料以 `earnings` 等明確頂層集合加入，不建立通用 `widgets`、plugin 或任意 `sections` schema。
- 工作台只顯示已經有資料的資訊區塊，不顯示尚未接通的 EPS、財報或其他功能占位。

## Testing Decisions

- 主要測試 seam 是 market snapshot JSON 合約。Pipeline 的 builder 應是可傳入固定資料、不碰網路的純函式，測試輸出的必要欄位、數值轉換、排序、新聞多分類、symbols 與 `generatedAt`。
- 前端保留一份可再散布的 toy snapshot，透過 TypeScript build 驗證消費端型別與實際資料形狀能整合，不另加 schema library。
- 新聞篩選與排序是包含多個分支的純邏輯，使用一個小型 Vitest 測試檔驗證市場／標的 scope、日期區間、多選分類與最新優先。
- UI 元件保持薄，只呼叫已測試的 selector 並呈現結果；第一版不新增 DOM 或瀏覽器測試框架。
- Pipeline 測試沿用現有 pytest 的 fixture 加純函式模式；前端測試沿用現有 Vitest 純函式模式。
- 完整驗證包含 pipeline 測試、前端測試與前端 production build。
- 測試外部行為與合約，不鎖定元件內部 state、CSS class 或 chart library 的呼叫細節。

## Out of Scope

- 即時行情、分鐘線、盤中自動更新與推播。
- 全市場掃描器、任意股票搜尋，以及前端新增或移除自選股。
- 台股以外市場的完整顯示與交易日規則。
- 均線、RSI、MACD、畫線工具或其他技術分析功能。
- EPS、財報、籌碼、社群情緒等尚未整合的資料與 UI。
- 通用 widget／plugin／sections schema，以及未來功能占位。
- 瀏覽器端翻譯、摘要生成或第三方 API 呼叫。
- 交易日曆、自動過期警告與排程更新。
- 將既有遊戲改成直接消費 market snapshot，或修改 `Scenario`。
- 第二種遊戲及完整的多遊戲路由系統。
- 公開部署真實新聞或真實 market snapshot。

## Further Notes

- 「工作台提供的資訊是各遊戲可取得資訊的母集合」是產品方向，不代表所有遊戲都要共用同一份大型 schema。每個遊戲應選取需要的市場資訊，再建立自己的互動合約。
- 第一版先證明每日資料從 pipeline 到工作台的完整路徑。只有第二個實際消費者出現時，才從現有實作中抽取更多共用能力。
- 真實財報與 EPS 的整理目前在 private repo 進行；在該資料合約成熟並可安全整合前，本專案不猜測其欄位。
